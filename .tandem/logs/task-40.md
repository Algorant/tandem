## Superseding direction from Algorant

This supersedes the earlier shared-ancestry/private-compaction proposal. Algorant clarified that immediate Git commitment of every metadata event is NOT a requirement. The actual requirements are: (1) ordinary Worktrunk operations/merges back to main must not be disrupted by Tandem housekeeping; (2) when committing/pushing, pending tracked and untracked .tandem files are automatically collected and committed, rather than left behind or repeatedly escalated as unexplained untracked files. Metadata is expected repository state, not unrelated junk the user should babysit.

## Simple intended model

Native Tandem commands persist record/event files immediately, but normal Task activity does not amend/rebase/squash or manufacture a Git commit per event. Batch pending metadata until a deliberate source commit/push boundary. At that boundary, the workflow invokes one native, forward-only checkpoint path automatically, collecting new files, modifications and deletions within the owning .tandem directory. A clean flush is a no-op; metadata-only work gets an ordinary checkpoint without a fabricated source/empty commit. Source-first then one forward metadata checkpoint is acceptable; do not reintroduce amendment merely to force everything into one commit. Never rewrite an existing commit to absorb late-arriving metadata: later changes belong to the next boundary.

Remove/supersede automatic amend/reconciliation/folding behavior and the automatic lifecycle-boundary Git triggers that create history spam; keep immediate record persistence, stable outcomes and one authoritative native metadata Git writer. Do not layer branch-reachability heuristics over the old design. Audit every trigger, including lifecycle operations and explicit no-change checkpoint, to ensure no hidden history-rewrite path survives. Preserve unrelated staged/unstaged/untracked source changes. Keep batching automatic at the host workflow boundary, NOT a newly required manual command for Algorant.

## Native vs adapter ownership

Core Task owns native checkpoint/persistence policy, tests and protocol guidance. Existing core rules prohibit editing external Pi adapters without a separate Task. Identify and provide an exact adapter handoff for any necessary changes to commit/push hooks/guidance, metadata warnings, or Worker integration behavior. Do not claim end-to-end user requirements solved if native implementation ships without required adapter wiring. Orchestrator must refresh the existing Worker's contract and replan/dispose any wrong-boundary old attempt through normal ownership tools. No Worker ownership transfer is authorized by the peer notification.
